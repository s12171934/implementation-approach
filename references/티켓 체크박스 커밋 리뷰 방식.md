# 티켓 체크박스 커밋 리뷰 방식

> 슈퍼프로젝트의 최상위 코디네이터가 설계문서를 기준으로 티켓마다 서브모듈 워크트리를 두고 [[티켓 체크박스 커밋 리뷰 루프]]를 돌리는 구현 방식이다. **몇 개를 동시에 돌릴지는 방식이 아니라 티켓 착수 시 정하는 파라미터**다.
> 루프의 내용은 [[티켓 체크박스 커밋 리뷰 루프]]가 SSOT이며, 이 문서는 그 루프를 **몇 개 띄우고 누가 감독하는지**만 정한다.

## 적용 조건

- 아래가 모두 성립할 때 이 방식을 고른다.
- 실행 위치가 서브모듈을 가진 슈퍼프로젝트다(`.gitmodules` 있음).
- 설계문서가 확정되어 있고, 그 문서를 담은 워크트리가 있다.
- 구현 범위가 지라 티켓으로 쪼개져 있고, 각 티켓 본문이 체크박스로 나뉘어 있다.
- 티켓 체크박스에서 커밋 단위가 나온다.

- 아래 중 하나라도 해당하면 이 방식이 아니다.
- 티켓 체크박스에서 커밋 단위를 끌어올 수 없다.
- 커밋을 만들지 않는 작업이거나, 지라를 쓰지 않는 저장소다.

## 구조

| 역할 | 사는 곳 | 소유 |
| --- | --- | --- |
| 최상위 코디네이터 | 슈퍼프로젝트(서브모듈을 가진 저장소) | 티켓↔워크트리 대응과 진행 순서, 워커 생성 계획, 회차 루프 운영, 워크트리 코디네이터를 하위 코디네이터로 감독, 결정 필요 사항 취합, 사용자 보고 |

- **워크트리 코디네이터 이하의 역할은 [[티켓 체크박스 커밋 리뷰 루프]]가 정의한다** — 이 문서에 복제하지 않는다.
- **최상위 코디네이터는 코드를 쓰지 않는다** — 슈퍼프로젝트에 상주하며 감독만 한다.
- **감독자 없는 코디네이터를 두지 않는다** — 최상위는 워크트리 코디네이터들의 완료 보고를 끝까지 받는다.
- **자기 워크트리 밖은 읽기만 한다** — 쓰기는 자기 워크트리와 볼트로 한정된다 (`vault-write-boundary` 스킬).
- 워크트리 밖 읽기는 **언제나 절대경로**로 한다 — 워커 세션의 작업 디렉터리가 워크트리로 고정되어 상대경로가 엉뚱한 곳을 가리킨다.

### 동시 트랙 수

- **동시 트랙 수는 워커 생성 계획 뒤, 회차 루프에 들어가기 전에 사용자가 정한다(1·2·3·제한 없음). 기본은 1 이다.** 방식을 가르는 축이 아니므로 값이 달라져도 오버라이드가 아니며, 그 값과 근거는 최상위 코디네이터의 작업 폴더에 남긴다.
- **트랙을 2 이상으로 올리려면 아래를 전부 만족해야 한다.** 하나라도 서지 않으면 1 이다.
  - 티켓 간 계약 의존이 디스패치 전에 동결됐다.
  - 트랙끼리 같은 파일 경로를 쓰지 않는다 — 저장소가 서로 다르면 자동으로 충족된다.
  - 각 트랙이 자기 워크트리 밖을 쓰지 않는다.
- **트랙이 1 이면** 살아 있는 워크트리 코디네이터는 하나다. 앞 배치 단위가 닫히기 전에 다음 워크트리를 만들지 않고, 앞 티켓에서 확정된 계약을 다음 티켓 스펙에 리터럴로 옮긴다 — 순서가 의존을 지우는 자리다.
- **트랙이 2 이상이면** 티켓마다 워크트리 하나가 동시에 산다. 올라온 정정은 최상위가 즉시 다른 트랙에 전달한다.
- **트랙 수와 무관하게 동시에 사는 워크트리는 티켓당 하나다** — 여러 브랜치를 경유하는 티켓은 그 안에서 체크박스마다 차례로 쓴다 ([[티켓 체크박스 커밋 리뷰 루프]] 배치 단위 절).

### 같은 저장소 체인

- 같은 저장소의 티켓들이 브랜치를 쌓아 잇는 체인(스택)이면 **의존을 둘로 나눠 본다.**
  - **계약 의존** — 앞 티켓의 산출물(API·타입·컴포넌트)을 소비한다. 설계의 티켓 선행 관계가 이것이다.
  - **스택 순서** — 같은 저장소에서 브랜치를 쌓는 순서일 뿐 산출물을 소비하지 않는다.
- **착수는 계약 의존만 본다** — 계약 선행이 모두 verified 이면 띄운다. 스택 순서의 앞 티켓이 진행 중이어도 기다리지 않는다.
- **베이스는 체인에서 가장 가까운 verified 티켓의 verified 헤드다.** 없으면 저장소 베이스다. 진행 중인 앞 브랜치 위에서는 착수하지 않는다 — 앞 브랜치만 있으면 띄우던 규칙은 선행 커밋이 빠진 채 시작하는 결함을 냈다.
- 같은 저장소의 계약 선행 verified 헤드가 그 베이스의 조상이 아니면 착수하지 않고 멈춘다.
- **verify 만 체인 앞을 기다린다** — 첫 verify 체크박스는 체인 바로 앞 티켓이 verified 일 때만 돈다. 구현·수정 체크박스는 기다리지 않는다.
- **체크박스 경계에서 리베이스한다** — 더 가까운 verified 체인 헤드가 생기면 다음 체크박스를 띄우기 전에 그 위로 옮기고, 이미 그린이 된 테스트(와 타입 검사)를 다시 돌린다. verify 게이트를 통과하는 경계에서는 완료 기준 테스트 전체를 돌린다.
- 리베이스가 충돌하거나 재검증이 빨강이면 **자동 해소하지 않고 멈춘다** — 사람이 본다.
- 리뷰 세션이 작업 트리를 읽는 동안에는 리베이스하지 않는다.
- **verified 티켓은 체인의 접두사여야 한다** — 앞이 verified 가 아닌데 뒤가 verified 인 상태가 생기면 멈춘다.
- 이 체인은 트랙 2 이상의 「같은 파일 경로를 쓰지 않는다」 조건의 예외다 — 파일 겹침은 경계 리베이스의 충돌로 드러난다.

## 절차

1. **대응 확정** — 최상위 코디네이터가 설계문서의 티켓 맵과 티켓별 위상정렬 순서를 읽고, 지라 티켓이 그에 맞게 생성됐는지 대조해 티켓·브랜치·워크트리의 대응과 진행 순서를 확정한다. 적용 조건이 서지 않으면 여기서 끝낸다.
2. **워커 생성 계획** — Before the first dispatch, the owning coordinator registers every planned batch as an actual Task in its own Run and records the batch-to-Task mapping. Session-local `aplan` events and Markdown plans do not register a project worker roster. A delegated planner asks the owning coordinator to perform registration and waits for confirmation; it must not impersonate that coordinator. Reuse existing Tasks for the same Run and batch, preserve completed and running work, and keep contract dependencies separate from stack order. Verify the complete roster and dependencies in the dashboard data before reporting registration complete. Each ticket coordinator registers its detailed implementation, review, judgment, integration-review, and audit Tasks in its own Run before starting them.
3. **트랙 수 결정** — 「동시 트랙 수」의 조건을 근거로 사용자가 값을 정한다.
4. **회차 루프** — 계획한 배치 단위가 모두 끝날 때까지 아래를 되풀이한다. 실행 한 번이 루프를 끝까지 돈다.
   1. **현황·우선순위** — 지라 티켓 상태, 볼트 노트, 대시보드를 읽어 남은 배치 단위를 우선순위대로 정렬하고 이번 회차 판정(착수 · 대기 · 막힘 · 완료)을 낸다. 사용량은 보지 않는다 — 사용량 게이트는 워크트리 코디네이터 이하가 맡는다.
   2. **이월·워크트리 확보** — 우선순위 목록에서 빈 트랙만큼 배치 단위를 고르고, 확정된 계약을 위임 스펙에 리터럴로 옮긴다. 워크트리는 티켓이 속한 **서브모듈 저장소**에 Orca 워크트리로 만든다 — 프로젝트 번호 이름의 빈 프로젝트 워크트리를 한 번 만들어 재사용하고, 티켓 워크트리는 언제나 그 하위에 새로 만든다.
   3. **위임** — 배치 단위마다 워크트리 코디네이터를 최상위의 **하위 코디네이터(워커)**로 병렬로 띄우고 티켓 스펙과 [[티켓 체크박스 커밋 리뷰 루프]]를 넘긴다. 하위 코디네이터는 자기 배치 단위를 루프대로 끝까지 돌고 끝나면 worker_done 을 보낸다.
   4. **대기** — 띄운 하위 코디네이터 중 하나라도 끝날 때까지 기다린다. 착수할 것이 없어도 진행 중인 하위가 있으면 기다린다. 올라온 계약 정정은 즉시 다른 트랙의 하위 코디네이터에 전달한다.
   5. **대시보드 갱신** — 끝난 배치 단위의 결과를 대시보드 상태에만 반영한다. 구현 상세는 정리하지 않는다.
   6. 남은 배치 단위가 있으면 1 로 돌아간다. 막힘·사람 대기만 남았거나 회차 상한에 닿으면 루프를 끝내고 **중단 보고**를 한다.
5. **취합** — 모든 배치 단위가 끝난 뒤 한 번, 진행 중 볼트에 쌓인 노트를 모아 사용자가 결정해야 할 것을 「결정 필요 사항」 노트로 정리하고, 티켓별 브랜치 구현이력과 PR 리뷰 요청 게시 목록을 프로젝트 단위 목록으로 정리한다.
6. **보고** — 티켓마다 한 줄과 결정 필요 사항 요약으로 사용자에게 보고한다.

## 금지

- **최상위 코디네이터가 findings 를 직접 릴레이하는 것** — 릴레이가 한 세션에 몰려 위임의 의미가 사라진다.
- **같은 파일 경로를 두 트랙이 쓰는 것** — 같은 저장소 체인은 「같은 저장소 체인」 규칙을 따른다.
- **계약 의존이 남은 티켓을 동시에 띄우는 것** — 양쪽이 각자 발명한 계약으로 갈라진다. 스택 순서만 남은 티켓은 여기 해당하지 않는다.
- **워커 생성 계획 없이 첫 워커를 띄우는 것** — 드라이버를 쓰지 않는 수동 진행도 예외가 아니다.
- **확정되지 않은 계약을 다음 티켓 스펙에 포인터로 넘기는 것** — 계약은 리터럴로 옮겨 적는다.
- **한 티켓의 체크박스 브랜치를 동시에 띄워 티켓당 워크트리를 둘로 만드는 것.**
- **한 트랙의 게이트 대기를 다른 트랙으로 우회하는 것** — 계정 풀은 공유 자원이라 우회가 성립하지 않는다. 사용량 게이트 판정은 워크트리 코디네이터 이하가 한다.
- 루프 자체의 금지 사항은 [[티켓 체크박스 커밋 리뷰 루프]]가 그대로 적용된다.

## 완료 판정

- **티켓 단위** — 루프 문서의 티켓 완료 판정 그대로. 워크트리 코디네이터가 종료 보고 후 닫힌다.
- **전체** — 모든 티켓이 종료 상태로 전이되고, 브랜치별 구현이력과 PR 리뷰 요청 게시 목록이 프로젝트 단위로 취합됨.
- **최상위 코디네이터의 사용자 보고**는 티켓마다 한 줄 — 티켓 · 브랜치 · 워크트리 · 커밋 수 · 미해결 기각 수 · 이력 노트 경로.
- 게이트 대기, 계정 전환이 있었으면 그 사실을 보고에 함께 적고, 「결정 필요 사항」 노트의 분류별 개수와 경로를 함께 보고한다.
- 미머지 브랜치는 통합을 요청받지 않았으면 그대로 두고 브랜치 이름을 보고한다.

## 다른 룰과의 관계

- 루프의 모든 규칙 — [[티켓 체크박스 커밋 리뷰 루프]]가 SSOT다. 이 문서에 복제하지 않는다.
- 방식 선택 — [[구현 방식 카탈로그]], 진입점은 `implementation-approach` 스킬.
- 워크트리 배치·탭 명명·모델 고정 — `orca-work-placement` 스킬.
- 코디네이터의 감독 의무와 완료 대기 — `orca-orchestration-rules` 스킬. 이 방식을 고른 것은 감독형 진입을 승인한 것으로 본다.
- 볼트 밖 쓰기 경계 — `vault-write-boundary` 스킬.
